# 结构性创造力：在问题空间里创造

> 适用场景：问题长期难解、方案不断打补丁、讨论陷入局部优化、需要设计新机制时。
> 本文件是 SKILL.md 生成侧的展开；质疑侧工具见 `thinking-mechanisms.md`。

## 创造发生在问题空间，不是答案空间

结构性创造力不是靠脑暴产生更多点子。它发生在：**当前的问题表示方式让你觉得"不对劲"时，换一个坐标系。**

触发信号（命中任意一条，先检查问题表示，而不是继续在解空间里优化）：

- 问题长期难解，好几个方案都差一口气
- 方案在不断打补丁，每个补丁又引入新问题
- 讨论陷入局部优化，争论的变量明显不决定结果

换坐标系的具体动作：重新定义**目标、约束、状态、边界、失败方式**中的哪一个。

典型演化路径（问题被一步步重新表示）：

> 怎么写一个更好的 prompt？
> → 怎么建立 reasoning protocol？
> → 模型是概率求解器，真正需要设计的是不是它周围的运行环境？
> → context、state、control、validation、retry、recovery、stop condition、human handoff

问题从"如何让模型回答得更好"变成了"如何设计一个容纳概率组件不稳定性的可靠执行系统"。有创造性的不是最终用了什么技术，而是 problem representation 被换掉了。

## 结构迁移：找共享同一结构性问题的领域

把成熟工程机制（状态机、schema、验证、重试、可恢复性、observability、failover）迁移进来，但不是 analogy 点缀。真正有价值的动作是：

> 发现两个看似不同的领域，**共享同一种结构性问题**。

例：LLM 输出不稳定 ≠ 分布式系统节点失败，但共享同一层结构——**内部组件不能被假定为永远可靠，可靠性必须由系统层提供**。看见这一层之后，成熟工程思想才能重新组合，而不是生硬类比。

## instance → class → mechanism

面对一次具体问题，不只问"这次怎么解决"，多问一步：

> 这个问题是否暴露了一类**重复出现**的问题？
> 如果是，能不能设计一个机制，以后系统性地处理这一类？

> 一次 failure analysis → failure analysis protocol
> 一次复杂长任务 → 执行循环协议
> 一次开放问题发散 → 收敛协议

这是工程创造力最常见的形态：不是新点子，而是从实例抽出类别、从类别造出机制。

## 何时发明新机制

克制原则：**只有当现有抽象无法解释或解决关键 failure mode 时，才创造新机制。**

- 先问：这个 failure mode 是不是已有成熟机制（重试、灰度、状态机、校验）能覆盖的？
- 发现 failure mode 之后，优先改变导致它的**结构**，而不是给现有结构打补丁（例：与其在 prompt 里写"深入思考、不要过早下结论"，不如改变运行时面对的问题结构，让过早收敛的路径本身变得不容易）。
- 不为了新颖而创新。新颖是结果，不是目标。

注意对 LLM 的纠偏："要有创造力"这类指令会被理解成"多想几个不同方案"——那恰恰不是这种创造。优先寻找**能够改变整个解空间的新表示、新约束、新机制**，而不是在原解空间里增加备选项。

## 创造闭环

创造和问题解决必须连成一个循环：

> 重新定义问题 → 发明机制 → 做最小实现 → 暴露失败 → 更新对问题的理解 → 再改机制

任何新想法最终都要能回答：怎么最小实现？如何验证？最可能怎样失败？什么证据会推翻它？回答不了的 idea 不值得长期持有。创造的成品不是概念，是**能够运行、能够观察、能够被证伪的东西**，实现反馈回来重新修正对问题的理解。

## 一句话版本

> **Reframe → Reduce → Invent → Verify**：重新表示问题 → 找到支配结构 → 必要时创造新机制 → 用现实闭环。

这四步比"critical thinking / first principles"更接近创造的实际发生方式——因为创造力往往不发生在答案空间，而发生在问题空间。
